函数每被调用一次，只回答一个问题：**现在处于什么状态，下一步怎么走。**状态由两个参数完整描述：手头这门课还剩几小时（`currClassHoursLeft`），后面还排着哪些课（`classesAfterThat`）。

**第一层分岔：`if currClassHoursLeft == 0`。**问的是"当前这门课干完了吗"。没干完（`else`），走第 12 行；干完了，进 `match` 看课单。

**第 12 行：`doTheWork(currClassHoursLeft - 1, classesAfterThat)`。**这不是循环，是用递归调用表达"时间过去了一小时"。新调用里第一个参数少 1，第二个参数原样传下去——课单没动，因为你还在当前这门课里埋头。函数没有可变变量，"进度"只能靠把新状态作为参数传给下一次调用来体现。

**`match` 的两个 case：课干完之后看课单。**`classesAfterThat` 的类型是 `datatype classlist = NoneLeft | Cons(string, classlist)`，所以它只可能长成两种样子。`NoneLeft`：课单空了，全部干完，返回 `true`，递归到此为止。`Cons(cname, rest)`：课单非空，match 在此做的事是**拆开并命名**——把课单的第一门课的名字绑定给 `cname`，剩余课单绑定给 `rest`。这两个名字是你现场起的，只在这个 case 里有效。

**第 11 行：`doTheWork(classHours(cname), rest)`。**开工下一门课。第一个参数不是减出来的，是**重新装填**：`classHours(cname)` 查出新课的工作量，作为新的"剩余小时数"。第二个参数变成 `rest`——刚开工的这门课已经从"排队中"移到"进行中"，所以课单短了一节。

跑一个具体的例子。设 `classHours("A") == 2`，`classHours("B") == 1`，初始调用 `doTheWork(2, Cons("B", NoneLeft))`——正在干 A（还剩 2 小时），后面排着 B：

|步|hours|课单|走哪行|发生了什么|
|---|---|---|---|---|
|1|2|`Cons("B", NoneLeft)`|12|A 干掉一小时|
|2|1|`Cons("B", NoneLeft)`|12|A 再干一小时|
|3|0|`Cons("B", NoneLeft)`|11|A 完工，开 B：hours 装填成 1，课单弹出 B|
|4|1|`NoneLeft`|12|B 干掉一小时|
|5|0|`NoneLeft`|`NoneLeft` case|返回 `true`|

盯着表看两列的走势：第 12 行每走一次，hours 减 1、课单不动；第 11 行走的那次（第 3 步），hours 从 0 **跳回** 1，但课单变短。任何一步，要么课单变短，要么课单不动而 hours 变小——这就是 `decreases classesAfterThat, currClassHoursLeft` 这个词典序度量在每一次递归门口验到的东西。


// ---------- 例 2 sumTree / sumTreeList：互递归，Dafny 白送 ----------

// sumTree 调 sumTreeList，sumTreeList 又调回 sumTree。

// 但每一次跨越，传过去的都是对方参数的"子结构"：

// t.children 拆自 t；Cons(t,ts) 里的 t 和 ts 拆自整条表。

// 结构在严格缩小 => Dafny 自动搞定，一个字都不用写。

// （课上承诺：这种"子结构式"互递归永远不用你操心；

// 需要手写度量的互递归，看下面的 SumFrom。）

function sumTree(t : tree) : int

{

t.element + sumTreeList(t.children)

}

  

function sumTreeList(trees : list<tree>) : int

{

match trees

case Nil => 0

case Cons(t, ts) => sumTree(t) + sumTreeList(ts)

}


先把数据类型钉死，不然后面全是浮的。

```dafny
datatype list<T> = Nil | Cons (T, list<T>)
datatype tree = Node(element : int, children : list<tree>)
```

这个 `tree` 和 `btree` 不一样：它没有 `Lf`，**每棵树都是一个 `Node`**，带一个整数和一张"孩子列表"。孩子可以任意多——所谓的"叶子"，就是孩子列表为 `Nil` 的节点。所以一棵树长这样：

```
        Node(1, children)
        /       |
   Node(2,Nil)  Node(3, children)
                    |
               Node(4,Nil)
```

写成 Dafny 值：

```dafny
Node(1, Cons(Node(2, Nil),
     Cons(Node(3, Cons(Node(4, Nil), Nil)),
     Nil)))
```

**为什么必须两个函数。**你想求整棵树所有 `element` 之和。站在一个 `Node` 上，你手里有两样东西：一个 int，一张 `list<tree>`。int 直接加，但那张列表怎么处理？它是**列表**，不是树，`sumTree` 自己吃不下。于是需要一个专门吃 `list<tree>` 的函数——`sumTreeList`。而 `sumTreeList` 沿着列表走的时候，每一格里装的又是一棵**树**，它自己也吃不下，只能递回去交给 `sumTree`。两个类型互相嵌套（树里有树的列表，列表里有树），所以两个函数互相调用。这就是互递归——不是什么技巧，是数据类型的形状逼出来的。

**用上面那棵树走一遍：**

```
sumTree(整棵树)
= 1 + sumTreeList( [Node(2,Nil), Node(3,...)] )     ← 树交出它的孩子列表
= 1 + sumTree(Node(2,Nil)) + sumTreeList( [Node(3,...)] )   ← 列表拆出头和尾
= 1 + (2 + sumTreeList(Nil)) + ...                  ← Node(2)交出空列表
= 1 + (2 + 0) + sumTree(Node(3,...)) + sumTreeList(Nil)
= 1 + 2 + (3 + sumTreeList([Node(4,Nil)])) + 0
= 1 + 2 + 3 + (4 + 0) + 0
= 10
```

皮球在两个函数之间踢来踢去，但每一脚踢过去的东西都在变小。

**"子结构"是什么意思，为什么白送。**注释里那句话的全部内容就是：看每一次跨函数调用，传出去的参数是从哪来的。

- `sumTree(t)` 里调 `sumTreeList(t.children)`——`t.children` 是从 `t` **身上拆下来的一部分**。整个 `t` 是 `Node(元素, 孩子列表)`，孩子列表是它的零件。
- `sumTreeList` 里 `case Cons(t, ts)` 调 `sumTree(t)` 和 `sumTreeList(ts)`——`t` 和 `ts` 是从整条列表 `Cons(t, ts)` 里 match 拆出来的零件。

零件严格小于整体，拆的动作不可能无限进行——一个有限的值，拆一层少一层，拆到 `Nil` 就见底了。这和单函数的结构递归是同一条原理，只是拆的动作分摊在两个函数身上。Dafny 看得出这一点，所以一个 `decreases` 都不用写，和你已经知道的"结构递归白送"是同一笔账。

反过来对照才能看清边界：`doTheWork` 第 11 行传的 `classHours(cname)` 是**函数算出来的新数**，不是从任何参数身上拆下来的零件——所以那边不白送，要手写词典序。判据只有一句话：**递归传出去的东西，是拆出来的，还是造出来的。**拆的免费，造的自己付账。


// ---------- 例 3 SumFrom / SumFromNeg：互递归 + 手写度量 + 补前置条件 ----------

// 目标：SumFrom(i,n) = i - (i+1) + (i+2) - (i+3) ... +/- n

// 例如 SumFrom(3,5) = 3 - 4 + 5 = 4。

// 实现套路：加正数的活儿归 SumFrom，加负数的活儿归 SumFromNeg，

// 两人互相把 i+1 抛给对方，i 一步步爬向 n。

//

// 【度量】i 在变大、n 不动 => 真正变小的是距离 n - i（和 up 同一招）。

// 【坑】只写 decreases n - i 还不够！若一开始 i > n，

// i 只会越爬越远，永远撞不上 n => 对这种输入它"真的"不停机。

// 所以必须用 requires 把这种输入禁掉。

// （课上还给过另一条路：把判停条件改成 if i >= n ——防御式写法。

// 两种修法二选一即可，这里保留 requires 版。）

function SumFrom(i: int, n: int): int

requires i <= n // ★ 答案其一：禁止 i 从 n 的右边出发

decreases n - i // ★ 答案其二：度量 = 离终点的距离

{

if i == n then n else i + SumFromNeg(i + 1, n)

}

function SumFromNeg(i: int, n: int): int

requires i <= n // ★ 互递归的两边都要写

decreases n - i // ★ 同上

{

if i == n then -n else -i + SumFrom(i + 1, n)

}

// 互递归的终止检查是"跨函数"比的：SumFrom(i,n) 调 SumFromNeg(i+1,n) 时，

// 拿被调方的度量代入实参 n-(i+1)，与调用方的度量 n-i 比：恰好小 1，

// 且旧值 n-i >= 0 [通过]。反方向同理。

// 前置条件也顺带成立：进递归分支时 i != n 且 i <= n => i < n => i+1 <= n。

  

// 有了前置条件和度量，这条"单元测试式"引理就自动通过了：

lemma sum35() ensures SumFrom(3,5) == 4 {}




**第一步：这函数到底在算什么。**目标是正负交替的求和：从 `i` 出发一路加到 `n`，符号一正一负轮换，`i` 本身取正。`SumFrom(3,5) = 3 - 4 + 5 = 4`。注意交替的不是数字，是**符号**——这一点决定了整个实现的形状。

**第二步：为什么要两个函数。**单个递归函数每次调用做的事都一样，但这里每一步做的事**不一样**：这一步加正的，下一步加负的，再下一步又加正的。状态"当前该取什么符号"必须存在某个地方。这份代码的选择是：不存变量，把符号**编码进"现在轮到谁干活"**里——轮到 `SumFrom` 就贴正号（`i + ...`），轮到 `SumFromNeg` 就贴负号（`-i + ...`），干完把 `i+1` 抛给对方。两个函数轮流接球，符号自然交替。走一遍：

```
SumFrom(3,5)
= 3 + SumFromNeg(4,5)      ← 正号活干完，抛给负号方
= 3 + (-4 + SumFrom(5,5))  ← 负号活干完，抛回来
= 3 + (-4 + 5)             ← i==n，触底，返回 n（此刻轮到正号方，所以是 +5）
= 4
```

对照例 2：`sumTree`/`sumTreeList` 是被**数据形状**逼成互递归的，这里是被**行为交替**逼成的。两种成因，同一种结构。

**第三步：度量为什么是 `n - i`。**每次递归 `i` 变成 `i+1`——参数在**变大**。`decreases` 验的是变小的东西，所以不能写 `decreases i`。真正在缩小的是什么？终点 `n` 不动，`i` 在逼近它，缩小的是**离终点的距离** `n - i`：3→5 距离 2，4→5 距离 1，5→5 距离 0，触底。你那个"递归门口验模具"的画面在这儿照用，只是模具量的不是参数本身，是参数的一个算式。`upList`/`upToNList` 是同一招——凡是"往上数到某个界"的递归，度量都是"界减计数器"。

**第四步：坑——为什么还要 `requires i <= n`。**`decreases` 只是一份**声明**，Dafny 还要替你验它真的每步在减、且减不穿零。设想从 `SumFrom(7,5)` 出发：`7 != 5`，递归调 `SumFromNeg(8,5)`，`8 != 5`，再调 `SumFrom(9,5)`……`i` 从 `n` 的右边出发，只会越爬越远，永远撞不上 `n`。这不是 Dafny 多虑——对这种输入它**真的**不停机。度量在这儿也如实暴露了问题：`n - i` 变成 `-2, -3, -4, ...`，一直在"减小"，但负数可以无限减下去，构不成必然触底的下降。所以 `decreases` 的完整规矩是：**每步严格变小，且旧值非负**。要满足"非负"，就得把 `i > n` 的输入用 `requires i <= n` 禁掉。两个函数都可能被从外部调用，所以两边都要写。

**第五步：Dafny 具体怎么跨函数验账。**单函数递归是自己跟自己比；互递归是**调用方跟被调方比**。在 `SumFrom(i,n)` 里调 `SumFromNeg(i+1, n)` 这一处，Dafny 做三件事：

1. 取被调方声明的度量 `n - i`，把实参代进去：`n - (i+1)`。
2. 与调用方当前的度量 `n - i` 比：`n-(i+1) < n-i`，恰好小 1，严格下降 ✓。
3. 验调用方当前度量非负：`n - i >= 0`——由 `requires i <= n` 直接给出 ✓。

反方向 `SumFromNeg` 调 `SumFrom(i+1,n)` 是完全对称的一笔账。

**第六步：前置条件自己也要传下去。**`requires` 不只约束外部调用者，**递归调用也是调用**——`SumFrom` 里调 `SumFromNeg(i+1, n)`，就得证明实参满足对方的 `requires`，即 `i+1 <= n`。它从哪来：能走到递归分支，说明 `i != n`；又有本方前置 `i <= n`；合起来 `i < n`，整数上等价于 `i+1 <= n`。成立。这条推理 Dafny 自动完成，但你要知道它发生了——将来你自己设计 `requires` 时，"递归调用处它还立得住吗"就是必查的一项。

最后那条 `lemma sum35() ensures SumFrom(3,5) == 4 {}` 没有新东西，就是 Lab4 Q8/Q10 那种 testing lemma：定义已被 Dafny 接受，具体数值它展开就能算。它放在这儿的意义是收尾确认——终止和前置都摆平之后，这个函数才成为一个可以被引理谈论的、真正存在的数学对象

**一、度量可以是算式，不必是参数。**之前你验的模具都是某个参数本身（列表、小时数）。这里第一次出现"参数都不在变小，变小的是它们的组合"——`n - i`。技能：看到计数器往上爬，反射性地写"界 − 计数器"。

**二、`decreases` 的完整规矩：严格下降 + 旧值非负。**之前的例子里非负是白送的（`nat`、列表长度天然非负），你意识不到它是条独立的规矩。`n - i` 是 `int`，可以为负，于是这条规矩第一次咬人——并逼出一个更深的认识：**终止性可能依赖前置条件**。`decreases` 和 `requires` 不是两个独立的坑，是一份合同的两半。Lab3 Q16 `fib_loop` 考的就是这个（题面明说"add a decreases _and_ a requires clause"），这是三个技能里最直接兑现成分数的一个。

// 再走一遍——这正是下周"手动调用引理做归纳"的预告片。

lemma sumClosedForm(i:int, n:int)

requires i <= n

decreases n - i

ensures SumFrom(i,n) == (if (n-i) % 2 == 0 then n - (n-i)/2 else -((n-i+1)/2))

ensures SumFromNeg(i,n) == -(if (n-i) % 2 == 0 then n - (n-i)/2 else -((n-i+1)/2))

{

if i == n {

// 基例：SumFrom(n,n) == n，公式给 n - 0/2 == n，Dafny 自动核对

} else {

sumClosedForm(i + 1, n); // 归纳假设：对更近一步的 (i+1, n) 成立

}

}

这段是从"写程序"跨到"证性质"的第一个完整样本，把它吃透，Lecture 8 的门就算进了。分两半：公式本身是怎么来的，证明是怎么走的。

## 上半：公式从哪来

闭式的意思是不用递归、一步算出答案的公式。推它只需要小学配对法。把和式写出来：

```
i - (i+1) + (i+2) - (i+3) + ... ± n     共 n-i+1 项
```

相邻两项从左往右两两配对：`i - (i+1) = -1`，`(i+2) - (i+3) = -1`……每对恰好贡献 -1。于是只剩数数问题——项数配不配得完：

- **项数为偶**（等价于 n−i 为奇）：全部配完，共 (n−i+1)/2 对，每对 −1，结果 = −(n−i+1)/2。
- **项数为奇**（等价于 n−i 为偶）：配完剩一个落单的末项 +n，前面 (n−i)/2 对各贡献 −1，结果 = n − (n−i)/2。

拿 `SumFrom(3,5) = 3−4+5` 验：三项，`3−4` 配成 −1，剩 `+5`，得 4；公式 n−i=2 为偶，5 − 2/2 = 4。对上。`ensures` 里那个 `if (n-i) % 2 == 0 then ... else ...` 就是把这两种情况写成一个表达式。

第二条 `ensures` 说 `SumFromNeg(i,n)` 恰好是它的相反数——从展开看很直观：`SumFromNeg` 的每一项符号都和 `SumFrom` 逐项相反，整个和自然差一个负号。

## 下半：证明怎么走

**为什么两条 ensures 挤在一个 lemma 里。**这是本例真正的新技能。函数是互递归的：`SumFrom` 的值依赖 `SumFromNeg`，反之亦然。所以证 `SumFrom` 的公式时，中途必然需要"关于 `SumFromNeg` 的知识"；而如果 `SumFromNeg` 的结论写在另一个 lemma 里，那个 lemma 又反过来需要这个——两个引理互相等对方，谁也起不了步。解法就是注释里那句"归纳时两条互相喂"：把两条结论捆成**一个** lemma，让归纳假设一次性同时供货。互递归的函数，配互递归（此处合并成自递归）的证明——证明的形状跟着函数的形状走，这是条通则。

**lemma 体里那行递归调用是什么。**`sumClosedForm(i + 1, n);` 是这整段代码最要紧的一行。lemma 体是语句的世界（你的三分类：函数体装表达式，lemma 体装语句），调用一个 lemma 是一条语句，效果是：**把它的 ensures 作为已知事实注入当前上下文**——前提是实参满足它的 requires。所以这一行的完整含义是："对 (i+1, n) 这个更小的问题，两条公式成立"——这正是数学归纳法里的**归纳假设**。手写归纳证明时你说"假设对 k 成立，证对 k+1 成立"；在 Dafny 里，"假设对更小的成立"不是说出来的，是**调自己**调出来的。

**有了归纳假设，Dafny 补的最后一步。**站在 else 分支里，Dafny 手上有：函数定义 `SumFrom(i,n) = i + SumFromNeg(i+1,n)`（展开一层白送），加上刚注入的事实 `SumFromNeg(i+1,n) == -(公式在 i+1 处的值)`。代进去，剩下的就是纯整数代数——验证 `i − (i+1 处的公式)` 恰好等于 `i 处的公式`，奇偶讨论和除法 SMT 求解器自己扛。基例 `i == n` 那个分支体是空的：`SumFrom(n,n) = n` 展开即得，公式给 `n − 0/2 = n`，自动核对。

**为什么 lemma 也要 `requires` 和 `decreases`。**`requires i <= n`：ensures 里谈论了 `SumFrom(i,n)`，而这个函数自带前置条件——lemma 想合法地提到它，就得先满足它的入场券。`decreases n - i`：lemma 调用自己，同样是递归，同样要过你那道验模具的门——这里防的是"循环论证"：如果归纳假设没有在严格更小的实例上取用，那就是拿结论证结论。度量沿用函数自己的 `n - i`，因为证明是踩着函数的递归结构走的，每步递进方向一致。顺带一笔账：调用处还得验 `i+1 <= n`，推理和函数那边一字不差——else 分支里 `i != n` 且 `i <= n`。

## 收账

这段代码的骨架值得你原样记住，因为它是往后所有递归证明的模板：

```
lemma 关于f的性质(与f相同的参数)
  requires 与f相同的前置
  decreases 与f相同的度量
  ensures  要证的等式
{
  基例分支 { /* 通常为空 */ }
  递归分支 { 调自己(更小的实参); /* = 取用归纳假设 */ }
}
```

Lab3 Q13/Q14、Lab4 Q11/Q12/Q14/Q15 全是这个骨架的实例，差别只在：它们取用的不是自己，而是 `lengthAppend`、`member_append`、`subset_member` 这些**别人**——但"调用 lemma = 注入已知事实"这个动作，和这里一模一样。


// ---------- 例 4 ackermann：字典序度量再现 ----------

// 三处递归，逐一看谁在变小：

// ackermann(1, m-1) —— m 变小（n 跳到 1，随它去）

// ackermann(ackermann(n-1,m), m-1) —— 外层：m 变小

// （第一参数爆炸式变大，随它去）

// ackermann(n-1, m) —— 内层：m 持平，n 变小

// 所以 m 是金牌、n 是银牌。默认参数顺序 (n, m) 恰好反了 => 必须手写：

function ackermann(n : nat, m : nat) : nat

decreases m, n // ★ 答案：m 主导，写在前

{

if m == 0 then n + 1

else if n == 0 then ackermann(1, m - 1)

else ackermann (ackermann(n - 1, m), m - 1)

}

先把词典序的比较规则钉死，再逐个调用点对账。

**规则。**`decreases m, n` 的意思是：把每次递归的度量看成二元组 `(m, n)`，比较像比奥运奖牌榜——先比第一位 `m`（金牌），`m` 严格变小就算赢，**第二位随便涨**；只有 `m` 持平时，才看第二位 `n`（银牌），此时 `n` 必须严格变小。另外每一位都是 `nat`，非负白送。

**逐个调用点对账。**函数体里有三处递归调用（第三处藏在第二处的参数里），每一处都要单独过一遍验模具的门。当前度量是 `(m, n)`：

1. `ackermann(1, m - 1)` → 新度量 `(m-1, 1)`。金牌 `m-1 < m`，赢定。银牌从 `n`（此处为 0）跳到 1——涨了，但金牌已分胜负，**随它去**。
2. 外层 `ackermann(ackermann(n-1, m), m - 1)` → 新度量 `(m-1, 天文数字)`。第一参数是一次完整的 Ackermann 调用的结果，大到没法想——不重要，金牌 `m-1 < m`，照样赢。这一处是词典序威力的极致展示：**只要主位在降，副位可以任意爆炸**。
3. 内层 `ackermann(n - 1, m)` → 新度量 `(m, n-1)`。金牌持平，看银牌：`n-1 < n`，赢。这一处就是 `m` 单独做度量不够的原因——`m` 在这儿纹丝不动，必须有 `n` 补位。

三处各自的"谁在变小"合起来，恰好是词典序的两种赢法各占其位：1、2 靠金牌，3 靠金牌平、银牌降。缺 `m` 则 2 处死（第一参数暴涨），缺 `n` 则 3 处死（`m` 不动）——两个都不可省，且**顺序不可换**。

**为什么必须手写。**Dafny 的默认行为是按参数声明顺序取度量，此处即 `decreases n, m`。拿它去验第 2 处：金牌位是 `ackermann(n-1,m)` 对 `n`——涨了，直接判负。默认顺序恰好把金银牌发反了，所以这是少数结构上很像能白送、实际必须动手的例子：不是 Dafny 看不出下降，是它猜错了**主次**。你只需告诉它谁主导：`decreases m, n`。

**一处容易漏的细节。**第 2 处的实参里嵌着第 3 处，这意味着要执行外层调用，得**先**算完内层——所以内层调用自己也要过终止检查（上面第 3 条就是它的账），而外层的检查是在"内层已经返回某个 nat"的前提下进行的：无论它返回多大，都只是个金牌位不看的数字。嵌套递归的账是这样一层层分开结的，不是混在一起。

对照收账：`doTheWork` 的词典序是"课单降 / 课单平、小时降"，这里是"m 降 / m 平、n 降"——同一个模具。增量只有一条：**默认参数顺序未必是正确的主次顺序**，遇到多参数递归，先自己审一遍每个调用点谁降谁涨，再决定 `decreases` 里谁写前面。

这个函数确实反直觉，因为它不是为了算什么实用的东西而写的——它是数学家 Ackermann 构造出来的"增长速度炸弹"，专门用来证明"存在可计算但增长快到离谱的函数"。但它的内部结构其实有一个非常干净的读法：**m 是运算的"级别"，n 是操作数**。先展开，再回头看每一行为什么长那样。

**第一步：逐级展开，看每个 m 是什么运算。**

m = 0：`ackermann(n, 0) = n + 1`。第 0 级就是"加一"。

m = 1：算几个值。`ack(0,1) = ack(1,0) = 2`；`ack(1,1) = ack(ack(0,1), 0) = ack(2,0) = 3`；`ack(2,1) = ack(ack(1,1),0) = ack(3,0) = 4`。规律：**第 1 级 = n + 2**，约等于加法。

m = 2：`ack(0,2) = ack(1,1) = 3`；`ack(n,2) = ack(ack(n-1,2), 1) = ack(n-1,2) + 2`——每递进一步加 2。所以**第 2 级 = 2n + 3**，约等于乘法。

m = 3：同法可推出 **2^(n+3) − 3**，约等于幂运算。m = 4 就是塔状指数，往上没有日常名字了。

现在模式清楚了：**每一级运算，是把下一级运算反复迭代出来的**。加法是反复加一，乘法是反复加法，幂是反复乘法——Ackermann 把"反复"这个动作本身递归化，一路叠上去。

**第二步：回头读三行代码，每行恰好是这个思想的一句话。**

`if m == 0 then n + 1` ——级别到底，最原始的运算：加一。整座塔的地基。

`else if n == 0 then ackermann(1, m - 1)` ——"第 m 级运算作用在 0 上"的起始值。迭代总得有个起点：乘法从加法迭代出来时起点是被加了一次的东西，幂从乘法迭代时起点是乘了一次的东西。这行统一规定：起点 = 下一级运算作用在 1 上。它是**迭代的初值条款**。

`else ackermann(ackermann(n - 1, m), m - 1)` ——核心。读作："第 m 级在 n 上的值 = 先算第 m 级在 n−1 上的值（**少迭代一次的结果**），再对它施加**一次**第 m−1 级运算。"对照乘法你就认识它了：`3 × n = (3 × (n−1)) + 3`——n 次乘法 = (n−1) 次乘法再加一次加法。嵌套调用里，内层 `ackermann(n-1, m)` 是"前 n−1 次迭代的累积"，外层套的 `ackermann(·, m-1)` 是"再来一次低一级的运算"。

**第三步：拿最小的非平凡例子走一遍，验证这个读法。**算 `ack(1, 2)`（第 2 级、约等于乘法，作用在 1 上，预期 2·1+3 = 5）：

```
ack(1,2)
= ack( ack(0,2), 1 )        ← 先算少一次迭代的，再施一次"加法级"
= ack( ack(1,1), 1 )        ← ack(0,2) 是初值条款：降级、操作数置 1
= ack( 3, 1 )               ← ack(1,1) 按第 1 级算出 3
= 3 + 2 = 5                 ← 第 1 级就是 +2
```

**第四步：这才解释了终止性那笔账为什么长那样。**结构看懂之后，前面对过的三个调用点全部有了含义：

- 走"初值条款"时降级（m−1），操作数重置为 1——所以 n 跳到 1 无所谓；
- 走"核心行"外层时也在降级（m−1），操作数是低级运算即将处理的一个巨大中间结果——大就大，级别降了；
- 走"核心行"内层时级别不变，纯粹是**同级少迭代一次**（n−1）。

"级别优先、同级看迭代次数"——`decreases m, n` 不是凑出来的技巧，是这个函数语义的直译：金牌 m 就是运算级别，银牌 n 就是迭代进度。度量写对的前提，从来是先懂函数在干嘛。你这次的追问顺序是对的。
